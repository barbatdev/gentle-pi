# feat(peers): add correlated guarded Pi peer-turn dispatch

## Parent and status gate

Parent: `https://github.com/Gentleman-Programming/gentle-pi/issues/442`. This draft is not approved or implementation-ready. B1 and B6a must be created, formally linked, reviewed, and accepted before implementation. B6b1 owns and implements its documented Pi runtime capability check; it is not an untracked prerequisite. B6b1 has no B2b2 dependency.

## Outcome

Connect B6a-authorized peer delivery to one guarded, correlated Pi receiver turn, bind exact peer-tool identities, and resolve registered platform lanes without making B6b1 a delivery authority.

## Evidence and scope

Peer dispatch is available only when the supported Pi runtime version is at least `0.84.3` and the runtime exposes documented `ctx.isIdle`, `pi.sendUserMessage`, input/message lifecycle, `before_agent_start`, blocking `tool_call`, `agent_settled`, and `session_shutdown`. A missing package, version, or capability disables peer dispatch only and reports unavailable; it has no fallback.

## Included scope

- One-shot correlation for one B6a dispatch record, guarded Pi enqueue, and visible redacted attribution derived from hidden verified state.
- A hidden principal/correlation entry, process-local lane registration SPI, and immutable peer-tool fingerprint checks.
- Turn-specific authority enforcement and bounded shutdown integration.

## Non-goals

No transport endpoint, wire ACK, dedupe, queue admission, trust or credential mutation, MAC-secret handling, retry, steering, generic peer tool, durable mailbox/history, platform lifecycle implementation, or fallback dispatch path. The registration SPI is not delivery authority.

## Normative contract

B6b1 implements the stated runtime capability check. It requires a supported Pi runtime `>=0.84.3` and every named capability. If any check fails, it disables peer dispatch only, reports unavailable, and does not substitute a transport or principal.

The one-shot correlation tuple remains exactly `(dispatch_id, B6a_dedupe_key, canonical_text_hash, input.source)`: `dispatch_id` is random, 128-bit, and non-secret; the dedupe key is B6a's exact key; `canonical_text_hash` is the hash of the exact attributed canonical text; and `input.source === 'extension'`. All values must match one atomically pending dispatch record, which is consumed once. Forged, replayed, mismatched, or no-pending input remains ordinary input and cannot activate the peer principal.

The verified hidden principal/correlation entry includes authenticated source peer ID, target peer ID, exact `project_scope_binding`, protocol epoch, generation, and dispatch ID. It includes no credential or secret. Public verified attribution is redacted and derives only from this entry. Text prefixes, peer names, or dispatch IDs alone never create a principal, badge, or hidden entry. Each triggering entry recalculates the principal.

B6a atomically reserves `queued -> dispatching`; that reservation permits exactly one synchronous Pi enqueue attempt, with no `await` between `ctx.isIdle()` and `pi.sendUserMessage`. The outstanding accepted-work capacity tokens remain counted on this transition. Idle uses `{expandPromptTemplates:false}`; busy uses `{deliverAs:'followUp', expandPromptTemplates:false}`. It never steers. Revocation or shutdown before the call terminalizes `queued` or pre-call `dispatching` with its before-delivery disposition, releases its capacity tokens exactly once, and permits no enqueue. Synchronous send success transitions `dispatching -> enqueued`. Once `pi.sendUserMessage` returns, Pi owns that queued user entry; Pi 0.84.3 exposes no selective removal of a specific queued `deliverAs:'followUp'` entry. An enqueued revocation or shutdown is therefore cancellation-pending with immutable eventual `revoked_during_turn` or `shutdown_during_turn`, not a zero-turn guarantee, and retains capacity until exact correlated settlement. A throw or ambiguous side effect fixes the exact entry's immutable disposition as `delivery_outcome_unknown`, with no retry or new wire ACK; its no-correlation quarantine retains capacity until session teardown unless exact correlated settlement proves no pending work. Only an exact correlated `before_agent_start` transitions `enqueued -> running`. Before provider or tool work, it rechecks B6a's credential-authorization and lane-admission projections. If invalidated or shutdown-pending, it activates deny-all rather than the normal three-wrapper allowlist, requests one abort for that exact correlated peer run, permits no tool execution, and retains the pending during-turn disposition. Human and unrelated runs are never aborted. Exact correlated `agent_settled` terminalizes a pending still-enqueued entry with its pending during-turn disposition and releases capacity; a normal nonpending still-enqueued entry terminalizes as `delivery_outcome_unknown` and releases capacity. A running invalidated or shutdown-pending entry receives one abort request, retains its during-turn disposition and capacity through the request, and releases capacity only at exact correlated `agent_settled`. `agent_settled` terminalizes a normal exact correlated running entry as `host_settled` and releases capacity; it is host lifecycle evidence, never a wire ACK or per-message completion.

B6b1 solely owns a process-local lane-registration SPI. Each lane has exactly `open(generation)`, `closing(generation)`, or `closed(generation)` and process-local handoff leases. B6b1 registration first synchronously publishes a version-bound open read-only lane-admission projection inside B6a; only after that publication succeeds does B6b1 open the lane. B6c or B6d acquires exactly one immutable `(lane_id, lane_admission_generation, handoff_lease_id)` lease only while its lane is open, then combines those exact identifiers with B4a or B5a platform-authentication context before B6a admission. A lease is neither an accepted-work capacity token nor queue or delivery authority, and model or envelope input cannot supply or override it. B6a admission checks the lease against its current projection and B6b1-issued lease authority; no, unknown, stale, mismatched, or released lease is rejected. The acquiring integration releases that exact lease exactly once in a finally-equivalent path after B6a returns any ACK or rejection, throws, or has an unknown connection outcome. Duplicate, unknown, or mismatched release fails closed and cannot affect another lease. B6a's accepted commit checks its current lane-admission projection; a stale, closing, or closed projection is `rejected`. For closure, B6b1 first atomically closes and increments B6a's projection so stale commits are rejected, then marks its lane closing and drains only unreleased old-generation leases; a publication failure is fail-closed. A late B6a commit remains rejected after projection close even while its lease awaits the `finally` release. B2b2 neither mutates nor calls this lane SPI. B6c and B6d register immutable `(lane_id, platform, project_scope_binding, sender_handle)` tuples. Duplicate matching platform and scope fails closed. Resolution requires exactly one current lane for the runtime platform and project scope; model and tool input never choose a lane. Registration carries no credential, trust, or delivery authority.

Before each B7a or B7b `registerTool`, that wrapper queries name-keyed `pi.getAllTools()` and refuses registration if the exact name already exists; its peer principal remains unavailable. After successful registration, B7a or B7b pins exactly one current `(name, sourceInfo.source, sourceInfo.path, sourceInfo.scope, sourceInfo.origin, sha256(canonical_json(parameters)))` fingerprint; a missing source field fails closed. `getAllTools()` does not expose overwritten history, so B6b1 does not claim historical duplicate detection.

At every peer-principal `tool_call`, B6b1 re-reads the one current definition and compares the full pinned fingerprint. A missing or changed definition, override, or schema drift blocks. The final normal peer allowlist is exactly the three fingerprints for `gentle_inspect_project`, `gentle_list_agents`, and `gentle_send_message`; name-only allowlisting is forbidden. Before B7 registration, the allowlist is empty. An invalidated or shutdown-pending exact correlated run instead has deny-all, so no tool can execute. Text without an exact pending correlation cannot activate deny-all or request an abort. The peer prompt is defense in depth; blocking `tool_call` is the authority boundary.

The process-local SPI exposes matching-identity unregister for B6c and B6d only after their closure barrier. `shutdownPeerDispatchOnce` is idempotent: it stops new dispatch; B6a terminalizes `queued` and pre-call `dispatching` entries as `shutdown_before_delivery`, releases their outstanding capacity tokens exactly once, and marks `enqueued` and `running` entries cancellation-pending with `shutdown_during_turn` while retaining their tokens until exact correlated settlement. It does not claim selective Pi queue removal after `sendUserMessage` returns. Exact correlated start activates deny-all and requests one abort only for that peer run; terminalization clears correlation. `session_shutdown` delegates only to this operation and releases no-correlation unknown-outcome quarantined tokens. It neither reopens admission nor creates fallback delivery.

## Dependencies

B1 and B6a. B6c and B6d consume this guarded dispatch integration, consume B2b2 endpoint-lifecycle events, and request their own matching lane closure while separately registering their lane tuples. B7a and B7b may register only their stated fingerprints after B6b1 is delivered.

## Acceptance criteria

- [ ] B6b1 verifies Pi `>=0.84.3` and every named runtime capability; failure is peer-dispatch unavailable only, with no fallback.
- [ ] The exact one-shot correlation tuple matches one pending record, and hidden/public attribution behavior cannot be forged from lookalike text.
- [ ] The hidden entry contains only the stated authenticated IDs, project scope, epoch, generation, and dispatch ID; public attribution is redacted and derived only from it.
- [ ] Idle/busy enqueue arguments, `queued -> dispatching -> enqueued -> running` correlation, no capacity release on dispatching, pre-handoff cancellation with exact release, absence of selective Pi follow-up dequeue after handoff, exact unknown-outcome and host-settled terminalization, settlement-only or teardown-only capacity release, no retry, no new ACK, and `agent_settled` lifecycle-only behavior are proven.
- [ ] An enqueued pending peer follow-up cannot abort a current human turn; a later exact correlated peer run rechecks credential and lane generation before provider or tool work, activates deny-all, permits no tool execution, and receives one peer-only abort; text or no-pending input cannot activate deny-all or request an abort.
- [ ] Lane registration is immutable and process-local with open/closing/closed generations and immutable leases; B6b1 publishes B6a's version-bound projection before open and closes/increments it before lane closure, while B6a admission checks that projection and B6b1-issued lease authority; B6c/B6d acquire exactly one lease and release that exact lease once on every ACK, rejection, throw, or unknown connection outcome; duplicate, unknown, or mismatched release fails closed; duplicate platform/scope and zero or multiple resolution fail closed, B2b2 has no lane call, and model/tool input cannot choose a lane.
- [ ] Before registration, a current-name collision refuses that wrapper; every peer-principal tool call re-reads and performs full immutable fingerprint comparison, and only the three stated wrapper fingerprints can be allowed after registration without claiming historical duplicate detection.
- [ ] Closure rejects new leases and accepted commits, waits only unreleased old-generation leases for at most 5 seconds through B6c/B6d, rejects late commits after projection close even before finally release, and preserves one terminal CAS, exact B6a shutdown dispositions, settlement-bound capacity release, correlation release, and matching-identity lane unregister without changing principal or send guarantees.

## Verification

Do not assert overwritten-history duplicate detection, selective dequeue, or name-only guarding. Run affected package tests.

## Rollback

Disable guarded dispatch and its lane/fingerprint registrations. Do not retry, create a wire ACK, alter transport, broaden the peer principal, or substitute a generic tool.
